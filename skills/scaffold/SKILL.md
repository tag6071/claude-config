# Project scaffold

Spin up a new project that already obeys CLAUDE.md from commit #1: native-first tooling, minimal deps, formatter + linter configured, runnable hello-world, green initial commit.

## Universal procedure

Apply to every scaffold, in order:

1. **Confirm scope.** Language? Project name? Subdir (default) or current dir (`.`)? Type (CLI / library / web / service) only if the request is ambiguous — single question with 2-3 concrete options, then proceed.
2. **Run native init** for the language (see playbook). Never reach for a third-party generator when the language ships one.
3. **Drop a runnable hello-world + ONE test** using the language's bundled test framework. The test must pass. "Live in the cabin before the cathedral."
4. **Configure formatter + linter** per the toolchain rule card (`~/.claude/lessons/toolchain-formatter-linter.md`). Config file in repo root, near-default content — no bikeshedding.
5. **Write a tight `.gitignore`** for the language (only what's actually generated by this toolchain).
6. **Run the formatter on all scaffolded files** so the initial commit is already green.
7. **`git init`** (if not done by the native tool) and initial commit: `chore: scaffold <lang> project`.
8. **Print a final report**: what was created, how to run it, how to test it.

## Hard anti-patterns (do not violate)

The default of most modern scaffolding is sprawl. Resist all of it.

- ❌ No framework scaffolds (Next, Rails, Django, Express, FastAPI) unless the user explicitly asks with `--with <framework>`. EXCEPTION: the React playbook below is the sanctioned path, invoked explicitly via `/scaffold react <name>`.
- ❌ No CI config (.github/, .gitlab-ci.yml, etc.) — separate concern, separate ask.
- ❌ No husky / lint-staged / pre-commit framework — the user's `enforce-green-commit.py` hook handles it globally.
- ❌ No TypeScript build pipeline for vanilla JS.
- ❌ No `Makefile` / `justfile` unless asked.
- ❌ No `LICENSE`, no `README.md`, no `CONTRIBUTING.md` unless asked.
- ❌ No dev deps beyond what each playbook below explicitly lists. If a "best practice" article says to add another, ignore it.
- ❌ For libraries: don't commit lockfiles. For apps: do.
- ❌ No `node_modules`-style auto-install of "useful" extras (eslint plugins, type packs, helper libs).

If you find yourself reaching for any of these, STOP and confirm with the user first.

## Per-language playbook

### Full stack (`/scaffold fullstack <name>`) — the default pairing, ONE command

The flagship path: Go backend + React `--saas` frontend in ONE repo, single-binary
deploy. This is a composition — it runs the two playbook paths below in order into the
same repo, then wires the contract between them. Don't make the user run two commands.

1. **One repo, backend at root.** `mkdir <name> && cd <name>`, then run the **Go SaaS
   backend** path (the `#### Go SaaS backend` section below) at the repo root — net/http +
   sqlc+pgx+Postgres + goose + slog, `cmd/server/main.go`, `internal/http,store`, `db/`,
   `api/openapi.yaml`. Green commit: `feat: add saas backend (...)`.
2. **Frontend into `web/`.** Run the **React `--saas`** path (the `#### --saas` section
   below) into the `web/` subdir (its own bun project) — Vite+Bun+TS, shadcn primitives,
   custom scale in tailwind.config, rhf+zod+`AppForm`, TanStack, router, three color modes.
   Green commit: `feat: add saas stack (...)`.
3. **Wire the pairing** (see `#### Pairing with a Go backend` below, the authoritative
   detail): `//go:embed all:web/dist` in `cmd/server/main.go` serving the built SPA
   (fallback to `index.html` for client routes); `web/` `bun run build` emits to `web/dist/`
   inside the Go module tree so the embed resolves with no copy step. Leave the
   `// TODO: generate from ../api/openapi.yaml` marker for the TS client codegen.
4. **`api/openapi.yaml` is THE contract — both halves are typed against it, never against
   each other.** This is what makes the real implementation cheap: the frontend is built and
   walked end-to-end against MSW handlers typed from the spec (`openapi-msw`/`orval` →
   `web/src/mocks/handlers.ts`), so by the time the Go handlers exist their job is only "make
   these responses real". Write the spec FIRST, before either half. Frontend work never blocks
   on the backend, and there is no shape-reconciliation phase at the end — the mock is not a
   detour before the build, it IS the build's spec. If a session finds itself hand-writing
   fake response shapes that the spec doesn't describe, the contract has been abandoned and
   the payoff is gone. (Full rules: the `mock-backend` rule-card.)
5. **Verify both halves green** (`go test ./...` + `bun test` in `web/`), then a final
   report covering the whole repo: layout, how to run backend (`go run ./cmd/server`) +
   frontend dev (`cd web && bun run dev`), how to build the single binary.

Result: one repo, one CI, one version tag, one deployable binary containing API + UI.
The canonical layout + every detail live in the two sections referenced above — this entry
just sequences them so it's a single command. (For a backend-only service use `/scaffold go
<name>-api`; for a standalone SPA use `/scaffold react <name>` ± `--saas`.)

### Go (zero external deps)
- `go mod init <module-path>`
- `main.go`: `package main` + `func main()` printing a greeting
- `main_test.go`: one `func TestGreet(t *testing.T)` that exercises a small extracted func
- `.gitignore`: `/bin`, `*.test`, `*.out`, `.DS_Store`
- Format: `go fmt ./...` (bundled). Lint: `go vet ./...` (bundled).
- Run: `go run .` — Test: `go test ./...`

#### Go SaaS backend (`--saas` / service — the default backend half of the full stack)

The base Go section above is for CLIs/plain services. This is the production backend path
that pairs with React `--saas` (single-binary deploy, OpenAPI→TS contract). Deps kept
minimal — pgx at runtime; sqlc + goose are dev/codegen tools. Everything else stdlib.

- `go mod init <module-path>`. Layout:
  - `cmd/server/main.go` — wires config (env via `os.Getenv`), `slog` logger, pgx pool, mux, graceful shutdown (`signal.NotifyContext` + `srv.Shutdown`).
  - `internal/http/` — `ServeMux` (Go 1.22 method+path routes: `GET /healthz` + one example resource route like `GET /api/widgets`); handlers take deps via a struct, no globals.
  - `internal/store/` — sqlc-generated code lives here; thin store wrapper over the pool.
  - `db/migrations/` — goose SQL migrations (one creating the example table).
  - `db/queries/` — hand-written SQL sqlc reads (one query for the example resource).
  - `sqlc.yaml` — engine `postgresql`, driver `pgx/v5`, queries `db/queries`, schema `db/migrations`, output to `internal/store`.
- Deps / tools: `go get github.com/jackc/pgx/v5`. Install dev tools and note them to the user (don't vendor): `go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest` and `go install github.com/pressly/goose/v3/cmd/goose@latest`. Run `sqlc generate` to produce `internal/store` code before first build.
- One `internal/http/*_test.go` using stdlib `testing` + `net/http/httptest` hitting the `/healthz` handler — must pass with no DB (handler-level, pool mocked or nil-guarded).
- `.gitignore`: `/bin`, `*.test`, `*.out`, `.DS_Store`.
- Format: `go fmt ./...`. Lint: `golangci-lint run` if installed, else `go vet ./...` (tell the user golangci-lint is the blessed linter for services — single binary, install once).
- Run: `go run ./cmd/server` — Test: `go test ./...` — Migrate: `goose -dir db/migrations postgres "$DATABASE_URL" up`.
- Escape hatches (document, don't default): chi (heavy middleware), GORM (if an ORM is demanded), SQLite via `modernc.org/sqlite` (small/local-first, no cgo).
- Commit the stack as its own green checkpoint: `feat: add saas backend (net/http, sqlc+pgx, goose)`.
- Pairs with the React `--saas` path → see "Pairing with a Go backend" under the React playbook for the `//go:embed all:dist` single-binary deploy and OpenAPI→TS contract.

### Rust (zero external deps beyond rustup)
- `cargo new <name> --vcs git` (binary) or `--lib` (library) — does init, .gitignore, hello-world, and initial git setup
- Add a test: if binary, append a `#[cfg(test)] mod tests { ... }` block to `src/main.rs` with one `#[test]` exercising an extracted function. If library, the default `it_works` test is already there — leave it or improve.
- Format: `cargo fmt`. Lint: `cargo clippy`.
- Run: `cargo run` — Test: `cargo test`

### Python (deps: uv + ruff; both single binaries from Astral)
- `uv init <name>` — creates `pyproject.toml`, `.python-version`, `.gitignore`, `src/<name>/` skeleton, sample hello file
- `uv add --dev ruff` — installs ruff into the project venv
- Append a `[tool.ruff]` block to `pyproject.toml` (near-default: `line-length = 100`)
- Replace uv's hello with `src/<name>/main.py` (real function + `if __name__ == "__main__":`)
- `tests/test_main.py` using stdlib `unittest` — ONE test against the function
- `.gitignore`: uv writes most of it; ensure `.ruff_cache/` is included
- Format: `uv run ruff format`. Lint: `uv run ruff check`.
- Run: `uv run python -m <name>.main` — Test: `uv run python -m unittest discover tests`
- NOT pytest unless the user asks.
- If `uv` is not on PATH: fall back to `python -m venv .venv` + `pip install ruff`, and tell the user "install uv (single binary from Astral) for 10–100× faster dep handling next time". Don't silently fail.

### Vanilla web (one dep: biome)
- For projects with no JS runtime needs (static HTML/CSS/vanilla JS).
- `index.html` (clean, valid HTML5, `<meta name="viewport">`, respects `prefers-color-scheme`)
- `style.css`, `main.js` — minimal, real, no placeholder lorem
- `biome.json` (near-default)
- `.gitignore`: `.DS_Store`, `dist/`
- Format: `biome format --write .`. Lint: `biome lint .`.
- Run: `python -m http.server 8080` (native, no install) — open `http://localhost:8080`
- No test framework by default; if the user later wants e2e, that's the `user-flow-test` skill's job.

### JS/TS app needing a runtime → Bun (deps: bun-init output + biome)
- `bun init` (interactive — accept defaults or pre-answer: name, entry, type=module)
- `biome.json` (near-default). Remove any default `tsconfig.json` strict-mode bikeshedding biome conflicts.
- `index.ts` (replace bun's default with something that exercises an exported function)
- `index.test.ts` using bun's built-in test runner — one test against the exported function
- `.gitignore`: ensure `node_modules/`, `bun.lockb` for apps stays IN, libraries OUT
- Format: `biome format --write .`. Lint: `biome lint .`.
- Run: `bun run index.ts` — Test: `bun test`
- If the user later says "bun is being a headache", fall back to Node + biome on next scaffold; don't preemptively switch.

### Ruby (one dep: standard)
- `bundle init` (creates `Gemfile`)
- Add `gem "standard"` to Gemfile, run `bundle install`
- `.standard.yml` (empty or `ruby_version: <current>`)
- `lib/<name>.rb` with a class/module + one method
- `test/test_<name>.rb` using stdlib `minitest/autorun` — one assertion
- `.gitignore`: `.bundle/`, `vendor/bundle/`, `*.gem`
- Format: `standardrb --fix`. Lint: `standardrb`.
- Run: `ruby -Ilib lib/<name>.rb` — Test: `ruby -Ilib -Itest test/test_<name>.rb`
- Standard over Rubocop: single tool, opinionated, no config wars.

### Shell (deps: shfmt + shellcheck assumed on PATH)
- A directory with a sample script `bin/<name>` (executable, shebang `#!/usr/bin/env bash`, `set -euo pipefail`, `main()` entry)
- `.shellcheckrc` (empty unless you have reason)
- `.gitignore`: `.DS_Store`
- Format: `shfmt -w bin/`. Lint: `shellcheck bin/*`.
- Run: `./bin/<name>` — Test: bats only if user asks.

### React app (deps: Vite + biome; via Bun to match the JS/TS playbook)

Base scaffold — minimal, runnable, green from commit 1. The full stack is opt-in (`--saas` below).

- `bun create vite <name> --template react-ts` then `cd <name> && bun install`
- Replace Vite's demo `App.tsx` with a minimal real component that calls one extracted pure util (e.g. `src/lib/greet.ts` exporting `greet(name: string)`), so the unit test needs no DOM.
- `biome.json` (near-default). Remove Vite's default eslint/prettier configs if present — biome is the one blessed tool per the toolchain rule card.
- One test with `bun test` against `greet()` (pure function, no DOM) — must pass.
- `.gitignore`: ensure `node_modules/`, `dist/`, `.DS_Store` (Vite's template covers most; this is an app, so the lockfile stays IN).
- Format: `biome format --write .`. Lint: `biome lint .`.
- Run: `bun run dev` — Build: `bun run build` — Test: `bun test`
- Initial commit: `chore: scaffold react project`.
- After the final report, if `--saas` was NOT passed, print one line:
  "Stack option: re-run with `--saas` for query + router + rhf/zod + shadcn wired in."
- If Bun is a headache on this host, fall back to `npm create vite@latest` + npm; don't preemptively switch.

#### `--saas` (the swear-by stack — only when explicitly requested)

Layer the production stack onto the base, deps listed explicitly (this list IS the sanctioned set; ignore "best practice" articles suggesting more):

- UI: `bunx shadcn@latest init` (sets up Tailwind + `components.json` + `lib/utils`). Then pull the primitives that ALWAYS get hand-rolled-and-wrong if absent — `bunx shadcn@latest add form button input select dialog popover dropdown-menu sonner` — so focus-trap/aria-modal/Escape-restore are present from commit 1. Pull anything else on demand; don't bulk-import the rest. You own the copied component code — that's the point. HARD RULE: styling is Tailwind utilities + tokens only — never CSS-in-JS (`<style>{…}`/`style={{}}`) or hand-written `.css` beyond the one global token sheet; never a native `<select>` or a `<div role=dialog>` when the shadcn component exists. (Mechanically enforced by the `stack-conformance` lint pack — `/install-lint-rails`.)
- Theme: bake in three color modes (auto/light/dark) from commit 1 — design tokens as CSS custom props in ONE global sheet (`src/index.css` `:root` + `[data-theme]`), wired through `tailwind.config`, plus a persisted, discoverable toggle (`localStorage`, defaults to auto/OS). One token source, one theme mechanism — never grow a second (it goes stale and they drift). Define your own spacing/type scale VALUES as a deliberate design step — this is where distinctiveness lives, so do NOT ship Tailwind's defaults (that's the generic look). (Choosing your own values constrains only where the numbers come from, not what style you build — any aesthetic is fair game.) In `tailwind.config` override `spacing`, `fontSize` (as `[size, { lineHeight, letterSpacing }]` pairs), and `letterSpacing` with your own ramp: a base unit + named rhythm, a modular type scale (your ratio). Prefer SEMANTIC keys so intent is legible — e.g. `fontSize: { label, meta, body, title }`, `spacing: { section, card }` → `text-title`, `gap-section`. This is the "named scale" your list wants, Tailwind-native (no second `--fs-*`/`--sp-*` CSS system). Then use only those tokens, never arbitrary px (`text-[13px]`). Let `gap`/`space-y` on a stacked container own vertical rhythm, not per-component margins. (Choosing the ramp/ratio: invoke the `frontend-design` skill.)
- Server state: `bun add @tanstack/react-query`; wrap the app in `QueryClientProvider` in `main.tsx`. Do NOT hand-write `useEffect` fetch logic. Mount `<Toaster />` (sonner) once at the app root for mutation feedback.
- Mock backend: `bun add -D msw @mswjs/data` + `bunx msw init public/ --save`. MSW intercepts at the NETWORK layer, so the app makes real `fetch` calls (via TanStack Query) with no mock-aware code — and the same `src/mocks/handlers.ts` serves the browser, Vitest and Playwright. Never hand-roll a fake API, never spin a side mock server (`block-mock-server.py` refuses it). Full rules: the `mock-backend` rule-card.
- Routing: `bun add react-router-dom`; one example route + a `BrowserRouter`.
- Forms + validation: `bun add react-hook-form zod @hookform/resolvers`. Two pieces, both mandatory:
  - `src/schemas/` — zod schemas are the single client-side validation source; the inferred `z.infer` types feed the forms. On a Go backend these mirror/derive from `api/openapi.yaml` (the cross-language contract — the Go handler validates the same shape server-side; client zod is convenience, the server is the gatekeeper).
  - `src/components/app-form.tsx` — a THIN (~30 line) glue primitive over shadcn `<Form>` + rhf (NOT a new form library — adopt rhf/zod/shadcn, build only the 20% convention; cite build-vs-adopt). Exports `<AppForm form onSubmit>` (wraps shadcn `<Form>` + `<FormProvider>`, calls `form.handleSubmit`) and `<SubmitButton>` which pulls `useFormContext()` and bakes in `disabled={!isValid || isSubmitting}` + a pending/spinner label (the double-submit guard rides on `isSubmitting`). Per-form, use the canonical shadcn pattern with a CONCRETE schema (don't write a generic `useZodForm` wrapper — it fights zod v4's input/output variance): `const form = useForm<z.infer<typeof schema>>({ resolver: zodResolver(schema), mode: 'onTouched', defaultValues })`. EVERY form uses this — it's why the disabled/loading/error/a11y UX can't be forgotten. (Proven tsc-clean + tested against react-hook-form 7.80 / zod 4 / @hookform/resolvers 5.)
  - One example form built with `<AppForm>` + a zod schema in `src/schemas/`, plus ONE Vitest test asserting (a) submit is disabled while the form is invalid and (b) a field error renders on bad input. Must pass (green commit).
- Tests switch to Vitest (the one justified deviation from the bundled runner — it shares Vite's transform pipeline): `bun add -d vitest @testing-library/react @testing-library/jest-dom jsdom`, add `test` script + `environment: 'jsdom'` to vite config, write ONE component render test. Must pass.
- API client: do NOT hand-roll one. Generate TS types + client from the Go backend's OpenAPI spec (see build-vs-adopt — adopt codegen, don't rebuild the contract by hand). Leave a `// TODO: generate from ../api openapi` marker, don't scaffold a fake client.
- Optional `--sentry`: `bun add @sentry/react`, add an error boundary at the app root.
- Commit the stack as its own green checkpoint: `feat: add saas stack (query, router, rhf+zod, shadcn, sonner)`.

#### Pairing with a Go backend (single-binary deploy)

**ONE repo, separate dirs — NOT separate repos.** `//go:embed` resolves at compile time
against the Go module's own tree, so the frontend's build output must live inside that
tree. Monorepo is mandatory, not a preference: one repo, one CI, one version tag.
Canonical layout:

```
<name>/
  go.mod                 # backend at repo root
  cmd/server/main.go     # //go:embed all:web/dist
  internal/http, store/
  db/migrations, queries/
  api/openapi.yaml       # contract → web/src types via codegen
  web/                   # the React app (its own bun project, package.json here)
    dist/                # bun run build output → embedded by go build
```

Documented handoff, do not auto-run as part of this scaffold:
- "Separately" below means a separate STEP and a separate DIR (`web/` + repo root), **in the same repo** — never a second git repo.
- Run the **Go SaaS backend** path at the repo root (see the Go playbook above): `/scaffold go <name>` → backend at root. That path is the default backend half of the full stack (net/http + sqlc+pgx+Postgres + goose + slog). Run the React `--saas` path into `web/`.
- In the Go service, embed the built frontend for a one-artifact deploy: `//go:embed all:web/dist` + serve via `http.FileServer(http.FS(...))`, falling back to `index.html` for SPA routes.
- Frontend `bun run build` (run from `web/`) emits to `web/dist/`, which sits inside the Go module tree so the embed path resolves directly — no copy step. Result: `go build` produces one static binary containing backend + UI that runs anywhere for years.

### Other language

- Ask the user to confirm the language.
- Research the single most-standard single-binary tool for that language's formatter + linter (e.g., for Zig: `zig fmt`; for Elixir: `mix format`).
- Surface the choice to the user with one sentence of reasoning. Wait for approval. Then proceed using the universal procedure above.
- Add the result to a follow-up note: "Worth adding <lang> to the scaffold playbook." Don't actually update this file — that's a separate change.

After the initial commit, print:

```
Scaffolded <lang> project at <path>.
Layout: <key files created>
Run:    <command>
Test:   <command>
Format: <command>
Lint:   <command>

```

Nothing more. The user reads the diff for details; the report is for orientation.
